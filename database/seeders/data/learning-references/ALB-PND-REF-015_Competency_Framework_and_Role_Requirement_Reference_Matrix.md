## 5. Why These Profiles Exist
The profile catalog is intended to provide legitimate coverage for the canonical organizational roles represented in the system without assigning profiles randomly or per employee.

A profile applies because its **position + department/context** matches the employee's current organizational record. Where the same title exists in different organizational contexts, separate profiles may define different requirements.

## 6. Exact-Level Basis
The exact required levels in this matrix are an **interim governed project baseline**, not a claim that Alibaton supplied an official competency matrix.

The baseline was structured using:

- role responsibility and independence;
- technical or operational complexity;
- safety/compliance exposure;
- review/approval responsibilities;
- supervisory or coaching accountability;
- the work expectations described by existing internal reference documents;
- consistency with the five-level proficiency model.

When the client provides official job descriptions, competency standards, certifications, or role matrices, affected requirements must be reviewed and a new profile version created when changes are material.

## 7. Operational Rule
Once a profile version is active, the system uses it as the fixed current competency standard for matching personnel. Admin/HR does not recreate the profile for every employee.

Changes to a published requirement should be handled through versioning rather than silent mutation.

## 8. Assessment and Gap Rule
Required levels become employee-specific competency status only when compared with **finalized validated assessment results**.

- no finalized assessment → Not Assessed;
- validated level below required → validated gap;
- validated level equal to or above required → requirement met/exceeded.

Learning or Training completion may support development evidence but does not directly change the validated proficiency level.

## 9. Change Control
This matrix and the machine-readable baseline must remain synchronized with the governed Competency Framework. Material changes require version review and historical traceability.

## Document Control
Any official client-issued source received later takes precedence and should trigger controlled review/versioning of affected competencies and role profiles.

## 10. Automation Boundary
The current system treats role requirements as governed standards but automates repetitive application of those standards. Employees are not manually assigned a competency profile one by one. The active profile is resolved from canonical workforce context, and current proficiency/gap/reassessment status is derived from governed records.

The project baseline therefore distinguishes:

- **Human-governed:** competency selection, required level, critical flag, evidence requirement, approval/publication, assessor authority, official rating/finalization.
- **System-owned:** employee/profile matching, applies-to classification when unambiguous, current proficiency, gap calculation, role-profile coverage, Learning/Training completion receipt, reassessment timing after completion, dashboard/analytics totals.

Data B remains the workforce authority for current personnel identity, position, department, person type, and reporting context. Data A remains the reference/governance authority for the interim competency framework and role-requirement baseline.
